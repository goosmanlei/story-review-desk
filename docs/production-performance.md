# 制作页面的读取、缓存与恢复

制作页面从当前动作所需的数据开始读取：目录不携带整部作品正文，列表不展开所有素材定义，视听制作只先展开目标镜头所选素材的完整当前方案或准确候选。准确详情仍使用权威修订；大卡完整正文、所选版本／候选、评论目标和操作控件到齐后才可用。优化不改业务原件、作品文字或准确选择事实。

## 请求和响应

- 启动只读实例、评论、配置概要、业务编号和资料／剧本目录。`/api/configurations?summary=1` 不枚举图标候选；进入配置页再读取完整候选。资料和剧本的 `metadata=1` 目录保留准确修订，进入故事页才读取正文。
- 素材管理使用 `grouped=1&compact=1&cards=1`。服务端保留全部组合筛选、分组身份、素材总数与展示总数，浏览器按既有分组与分页规则绘制。卡片读取不传已用于筛选的搜索字段和详细位置数组；准确范围开卡引用、目录、分组和计数保留，完整关联证据在大卡中读取。未指定 `cards` 的原接口保持完整字段，非 compact 接口仍返回完整投影。`cards=1` 只适用于 grouped compact 列表，不增加用户操作。
- 素材管理的视听目录按准确集修订复用，不把关键词、场、媒体或结果条件放入目录键；这些条件筛选同一目录，最终 HTTP 字节仍按完整查询区分。场必须属于所选准确集，历史集仍沿原组成读取。视听用途直接从准确组成、计划输入、备选和真实调用派生，不先构造随后会被替换的旧故事场用途。
- 搜索词每项只匹配一次，筛选计数按素材的准确集场用途集合一次汇总。每个选项只放宽它自己的条件，其他条件保持；重复用途不重复计数，场在另一集出现不能匹配当前集场。未命中选项仍保留零计数，不为各选项重新扫描全量素材及其用途。
- 视听制作使用 `/api/production/scene?view=reader`。返回整场所有镜头基础信息、全部直属需求（包括主／反机位和工程）、素材组及候选编号；先展开目标镜头和选中素材的完整参数、Prompt、准确参考。未选需求只传导航摘要，未选候选不展开提交快照。不存在的准确素材、候选或组成报错，不换为首项或最新结果。旧 `view=breakdown`、`view=shots` 及默认完整接口保留兼容用途，当前阅读路径不再同时构建旧 `context.video_details` 和新工作区。
- 进入实际可见镜头或切换素材／候选时，`/api/production/shot-materials?items=…` 自动读取最多3个准确目标。浏览器每个读区一次只发一个详情请求，合并同一在途选择；主动选择优先于可见邻镜。连续滚动无需折叠、分页或手动加载，补齐保留可见镜头位置。图片、音视频原件和波形仍按实际审阅需要读取，不作为正文可用的前提。
- 目录按准确集场镜组成批量取得直属素材的当前方案、真实候选及实际调用的评论身份，不展开完整方案、提交快照或共享上游素材。目录和场响应都返回只含编号、目标、版本与状态的评论计数索引；场响应还刷新本集的目标集合，后台新增候选／需求后不沿用旧计数。计数按评论去重，含已关闭，不把编辑历史计为新评论。页面本地后来保存的评论按更高评论版本合并。
- 同一目录内已知准确场／镜复用导航；同场已挂载镜头直接定位，不重新读取目录或场。同场定位不会取消仍属于当前读区的详情；离开读区或更换场时才使其失效。刷新、其他页签、另一集及未知目标重新读权威目录。
- 浏览器通过 Accept 协商 `application/vnd.review-desk.graph+json`。传输层把完全相同的对象、数组和长字符串编号一次，gzip 压缩后传输；解码恢复独立 JSON 树，不把两个不同版本或候选合并。普通 JSON 客户端仍获原有结构。此协议减少重复字节，不省略正文。
- JavaScript 和 CSS 按原顺序合并为两份带内容 SHA-256 的资源，支持 gzip、ETag 与一年 immutable 浏览器缓存。HTML 和业务 API 为 `no-store`。
- 原件不缩放、不改码、不迁移。媒体仍走原接口，分块读写；每次从同一个打开的文件计算 SHA-256，核对内容寻址文件名，再处理 ETag／Range。`private, no-cache` 允许浏览器在重新验证后复用准确字节；If-Range 不匹配返回完整内容。原件损坏报错，不用旧缓存掩盖。元数据归档仍按原方式无损还原。

## 读写链路与一致性

HTTP 使用固定 4 个工作线程、最多 8 个排队连接；监听积压上限 32，空闲连接 2 秒超时。每个工作线程拥有自己的 SQLite 连接和缓存连接，退出时关闭。初始化／迁移只由启动连接执行。业务库保留 DELETE 回滚日志：并发读取可以进行，写入提交等待活跃读快照结束；媒体传输不持有业务事务，缓存命中也只持有短读取快照。

本轮不启用 WAL。正式 Python 镜像内 SQLite 3.46.1 的 Debian 补丁集未包含 [WAL-reset 修复](https://sqlite.org/wal.html)，不能仅因使用多线程就自动转换。服务启动核对 DELETE 模式；已有 WAL 实例先停所有连接、SQLite backup 备份、checkpoint，再明确转换并核对，不能在活跃多进程中隐式切换。未来需要 WAL 时先核验全部读写进程使用已修复的 SQLite，再重新验证实际挂载、读写竞争和恢复。

每个 GET 在一个读取事务中解释准确引用。已经打开的读操作保持其快照，写入后开始的请求使用新代号。前端选择序号防止迟到结果覆盖新选择；导航取消失去用途的请求，后端在集、镜头和素材的安全读取边界检查连接，已断开的读取不再组装或序列化后续详情。单条已运行SQL在原有线程和队列上限内完成，不杀线程、不扩大并发。评论刷新也只应用最后一次读取，避免连续写入后的新列表被旧响应覆盖。切集以最后请求的集为准；独立素材大卡使用自身准确版本参数，不能继承父卡或已关闭大卡的版本。配置和评论的版本检查、修改、回执读取已放在同一个 `BEGIN IMMEDIATE` 事务。素材选择、镜头参考和后台导入仍通过现有权威事务及版本校验。

生产子页切换、离开工作区及重新读取使上一轮目录、场和详情读取失效，包括视听与实体共用同一工作区的切换。返回同名子页属于新一轮选择；旧成功不能更新正文、地址、准确审阅对象或阅读位置，旧失败不显示为新页错误。当前请求的成功和失败仍正常呈现，可继续切页后返回。准确历史缓存、筛选、分页、展开和草稿按既有身份保留，不通过清空状态或限制加载中导航来避免竞争。`production_page_lifecycle.test.cjs` 补充目录、场及同名往返的有界检查；实例另做真实页面验收。

本机预览在服务启动时构建内容寻址静态包。修改前端源码后须重启该隔离服务，再刷新页面并核对新的脚本 URL；只刷新页面仍可能读取进程中冻结的旧包。

读取复用分三层：

| 层次／对象 | 键和依赖 | 生命周期、容量与恢复 |
| --- | --- | --- |
| 请求内完整修订、列表元数据、内容节点、素材编号及归属、关系编号映射 | 当前连接的读取快照、对象及准确修订；内容节点逐个校验 SHA-256 | 请求结束即清除；写入验证不使用跨请求投影 |
| 素材列表所需的关系端点、有效输入下标、历史输入缺失结果、别名及成员索引 | 同一读取快照和准确修订；输入仍验证关系端点、路线和条件 | 一次读取内复用；批量取得归属，不逐素材扫描全表；不展开无关 Prompt 或提交正文 |
| 可重建投影：素材列表、实体工作区、业务编号 | 实例身份、后端代码摘要、业务事务代号、对象／准确修订、关系布局文件摘要 | JSON 压缩存入独立缓存库；未命中从权威记录完整重建；不回写业务库 |
| 成功 API 的最终字节 | 上述身份，加路径、全部查询条件及 JSON／图传输、gzip 表示 | 仅完整成功 200 结果；错误、冲突、结果未知及写响应不缓存 |

实例身份包含真实数据库路径、设备／文件身份及后端源代码摘要。数据库被替换时服务拒绝继续使用旧连接，恢复后必须重启。历史修订、实体、素材版本、候选、筛选、分页、视图和表示方式进入键，不互相借用。关系布局文件内容变化也形成新键。

业务数据库使用 `read_generations` 以及各业务表 INSERT／UPDATE／DELETE 的事务内触发器。每次实际写入同时改变对应表的随机代号；键取全部表代号的摘要，故目前采用保守的整实例失效。以下入口不依赖调用方主动发缓存消息：

| 写入口 | 受影响的读取与保证 |
| --- | --- |
| 评论创建、编辑、关闭、恢复，评论归属和编号 | 列表计数、实体评论目标、评论相关响应失效；评论 API 本身每次读取并校验锚点 |
| 素材选择、镜头参考选定 | 关系、状态、方案、版本和列表响应全部失效；历史准确引用仍由原记录解析 |
| 后台素材／作品导入、配置修改、增量发布 | 新修订、内容节点、别名、成员、编号在权威事务内更新代号；其他进程下一个请求可见 |
| 回滚、失败或冲突 | 代号随业务事务回滚；失败结果不进入成功缓存 |
| 数据库恢复／替换、代码升级、布局文件变化 | 重启后的实例身份或准确摘要变化；旧缓存条目不可命中 |

缓存文件为实例 `.runtime/read-cache.sqlite3`，与权威 `.runtime/review.sqlite3` 分开，也采用 DELETE 回滚日志。总有效条目上限 128 MiB、2048 项，单项最大 32 MiB；按最近使用清退。每连接 L1 最大 16 MiB（4 个请求工作线程合计最多 64 MiB，另有启动连接）。缓存数据库页数限额约 256 MiB，使用增量回收，短写事务提交后移除回滚日志；记录的是逻辑条目上限，不能把文件大小或进程总内存误称为同一个限额。

跨进程填充用同一缓存库的租约合并相同请求，最多等待 15 秒，异常退出后租约到期可重建。这个期限仅用于崩溃恢复，不决定业务新鲜度。填充前后二次检查代号；不持有业务读取事务等待其他填充者。缓存读写忙、损坏或空间不足时退回权威读取；磁盘条目校验摘要，解压上限 64 MiB。不需要 Redis、订阅通知或定时清空才能保持正确。

## 启停、清空与回退

以下命令从系统仓库执行，`INSTANCE` 是实际实例根目录，不是任务工作树的默认值。正式实例必须沿故事项目发布流程，在共享窗口操作；先保留准确镜像、SQLite backup 备份与媒体清单。

```sh
python3 -m review_desk --instance "$INSTANCE" read-cache status
python3 -m review_desk --instance "$INSTANCE" read-cache clear
REVIEW_READ_CACHE=0 python3 -m review_desk --instance "$INSTANCE" serve --port 8765
```

`status` 通过正常 Store 初始化入口核对表结构后报告容量及代号；不是只读迁移检查器。`clear` 在业务事务中轮换代号并清除缓存条目，在线工作线程的旧 L1 和迟到填充也不能再次命中。清空不删原件、评论、准确选择或修订。缓存停用只影响可重建结果；有界线程和原日志模式继续生效。重新启用时允许从空库开始。

缓存文件损坏时先停本实例服务及其其他读取进程，确认路径与归属，再移除该实例的 `read-cache.sqlite3` 和它的回滚日志；如从实验版升级，核对并处理对应的旧 WAL／SHM 文件。重启自动重建。不能删除或用测试快照覆盖 `review.sqlite3`。读缓存不是备份，备份及恢复只以业务库和受管原件为权威。

代码回退可使用准确上一版镜像，保留当前业务库和原件，DELETE 模式无需回退。旧代码可读新增的普通 SQLite 触发器。实验 WAL 库转换时停止所有连接，完成 `PRAGMA wal_checkpoint(TRUNCATE)` 后再执行 `PRAGMA journal_mode=DELETE` 并核对返回值。移除新增触发器／代号表只在停机窗口及备份后进行，按 `sqlite_master` 中 `read_generation_` 前缀逐项核对；不恢复旧数据快照来撤销缓存功能。

## 验证边界

自动检查覆盖完整传输还原、组合筛选与分组、准确历史、事务回滚、后台写入、跨进程可见性、填充租约、清空、损坏回退、容量、并发版本冲突和 Range／缓存身份。首次未命中仍有重建成本；命中率不作为页面改善证明。机器、版本、冻结数据、冷热条件、原始样本、四分位数算法、CPU／内存及真实浏览器结果由故事任务交付包记录。真实交互与正式发布必须另行实际验收。
