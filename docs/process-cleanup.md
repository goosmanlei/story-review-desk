# Process resource lifecycle

A configured project owns each build, QA, packaging or deployment phase through `maintenance/process-cleanup.json`. Mutating instance entrypoints require `REVIEW_PROCESS_CONTEXT`, issued by `scripts/instance-process.mjs run --root PROJECT --task ID --phase PHASE -- COMMAND`. Read-only inspection is unchanged. The host delegates container maintenance under its own registered phase; running an inner container CLI does not create a second authority.

The registry and temporary workspace are separate. Before allocation, a phase records its project, host, random token, process PID/start identity and exact resource intent. After creation it freezes directory device/inode or Docker identity. Paths must be new, inside configured process roots, and outside retained paths. Docker objects require the task token and project labels; pinned transport aliases and immutable builder-helper pulls bind their original digest. Consumers and retained deliveries are explicit. Unknown or changed ownership never becomes permission to delete.

On success, failure or cancellation, the runner closes its child and directly removes disposable containers, networks, dedicated test volumes, builders/caches, image aliases and files. It verifies absence and preserves the original command failure code. Each build uses a dedicated `docker-container` builder; its helper image is reclaimed if this phase pulled it. An image promoted to a verified live instance remains until its last container consumer disappears. Current databases, actual media, credentials, formal history, recovery slots and unique Git work are never generic process resources.

Outputs needed by later phases must be outside the producer's scratch directory. Use `transfer --kind path --key PATH --consumer PHASE`, or an explicit delivery/recovery `retain --reason REASON`. The named consumer releases the output when it finishes. An unknown remote outcome keeps the minimum input needed to resume the same publication; it cannot be erased by completing the parent task. Once every phase and host is verified, `finish --task ID` clears abandoned consumer claims. The completion check rejects `RUNNING`, `WAITING_CONSUMERS` and `CLEANUP_REQUIRED`.

The runner redirects OS, npm and tool caches into phase scratch and periodically checks configured storage/reserve budgets. Tools with their own output flags must also use that directory. Project adapters audit escaped output and require a precise cleanup or retention declaration. This is a process contract, not a filesystem sandbox: an arbitrary tool cannot be assumed to honor environment variables.

An OS scheduler should run `sweep` on startup and every five minutes. Kernel locks release on termination or reboot; PID start identities avoid reuse mistakes. A surviving child prevents cleanup until it has exited. Interrupted cleanup is idempotent and resumes from resource receipts. Diagnostics keep only bounded exit metadata, with a seven-day / 100 MiB cap per configured project and host. Successful command output, full databases, images, traces and dependency trees are not retained as diagnostics.

VPS deployment uses the publisher's existing exclusive kernel lock and journal. `cleanup` removes journal-bound verifiers/importers and unused, digest-bound publisher image aliases. It never removes current/pending databases or partial clean slots during `RESTORING` or `SAVING`. `install-cleanup` installs a target-specific systemd service/timer from the exact publisher bundle; installation requires the current-release CAS and no pending publication. Normal deploy/rollback also clean process resources before returning. A disconnected SSH session requires a fresh remote cleanup/operation readback before the originating task can be complete.

No command performs global Docker pruning. Historical archives retain their existing retirement protocol; this lifecycle does not expire unique historical bytes by age.
